Agent Bus Guide

How the Discord agent bus connects Mick to the AI agents on each machine: what runs where, how a message travels, how each agent kind is set up, and what is live versus still in review.

Describes router and clients at main 98038f6 (PR #12 and #18 deployed 26 Nov 13:23Z). Machine inventory surveyed read-only at about 18:25Z the same day. Secrets, tailnet addresses and full hostnames are deliberately left out; machines are named by their short box names.

In one paragraph

Mick talks only to Discord. A bot called mickbot runs inside one Docker container on vps2; that container is the router. Every agent session (Claude, Codex, opencode, agy, grok) runs a small MCP client that holds a WebSocket to the router over Tailscale. The router turns each Discord post, slash command or button click into mail, writes it to a durable inbox, and wakes the right agent. Agents answer through MCP tools (reply, bus_post, channel_post, …), and the router mirrors every agent post back into Discord so Mick can read the whole conversation. Each machine also runs a node daemon that can wake an agent for a headless turn when no terminal session is open. Bus v4 replaces the per-session clients with one gateway per machine that talks to each agent in its own native protocol; that part is written and in review, not deployed.

Section 1

The big picture

Three tiers. Discord is the only surface Mick uses. The router is the only thing that talks to Discord. Each machine connects to the router, never to Discord directly, and never to other machines.

The three tiers

TierWhat it isWhat it does
DiscordA private server with #general (the bus channel), topic channels, #human-questions and an archive category.Mick reads everything here and types here. The bot also registers slash commands and posts buttons and select menus.
RouterOne Bun process, src/router.ts, in the agent-bus-router container on vps2, next to a Tailscale sidecar.Owns the Discord connection, routing, the durable inbox, claims, subscriptions, the shared-MCP registry and grants, the wake budget and the rules. State lives in one directory on the host.
Machinesmac (Mick's laptop) and nas642. Each runs agent sessions, a node daemon, and later a gateway.Hold the agents. Each session's client keeps one WebSocket to the router; the node daemon keeps another for headless wakes.

Wakes and the durable inbox

Every directed message is written to an append-only, fsynced journal before any wake is attempted. A wake only tells the agent that mail is waiting; the agent reads it itself with check_inbox. Wakes are limited by a budget of 20 headless turns per hour per agent. On the pending gateway path the agent takes a lease on its mail and returns a receipt to acknowledge it, so an unanswered message is offered again rather than lost. Publish ids make retries safe: the same post sent twice within 24 hours is delivered once.

Section 2

How a message travels

Who receives a post from Mick LIVE

The router applies these rules in order. The audience starts as everyone for #general and #human-questions, and as the subscribers for a topic channel.

Mick writesWho gets it
@all, @all:independent, @all:synthesisEvery session in the audience, cheapest first. synthesis asks each to read earlier replies before adding anything.
@name … or name: …That one session, if the name matches exactly. A typo or a prefix that matches several names goes nowhere, and the bot says so in the channel.
A reply to an agent's postCarries the original as in_reply_to, so the agent sees what is being answered. In #human-questions only the asker receives it.
Anything elseThe dispatcher, if one is configured and online; otherwise the topic channel's owner; otherwise every live interactive session in the audience. Headless node agents are never woken by an untargeted post. Today no dispatcher and no channel owners are configured, so the last rule applies, and the bot notes "routed to … (no dispatcher; live interactive only)".
Pending, PR6 (master election, spec A10): sessions on an allowlist register as master candidates. The router elects one, holds a lease with a term number, and moves to the next candidate if the master stops renewing. Untargeted posts then go only to the master (or a topic owner), which assigns exactly one owner. This removes the duplicate-owner problem seen three times on 26 Nov. A coordination-only seat, claude@mac:swarm-master, already runs and assigns work by hand while the PR is written.

Section 4

Agent kinds and their profiles

"Profile" here means the per-kind configuration that puts an agent on the bus: the config file that declares the MCP client, the environment that names and wakes it, and how the node daemon resumes it headless. Every kind uses the same client binary; only the wiring differs.

Names

A session's bus name is DISCORD_SESSION_NAME if set, otherwise <agent>@<host>:<project dir>, where host is DISCORD_HOST_LABEL or the short hostname. If that name is already taken by a live session, the newcomer gets a -2 suffix. An explicit name takes over the old holder, which is told it was replaced and stops reconnecting.

Putting a new agent on the bus

  1. Host first. The machine needs Tailscale, Bun, the runtime checkout in ~/.local/share/agent-bus/multi-channel-discord and the host .env (router URL, router secret, host label). The ops repo README, mickg-containers/vps2/agent-bus/README.md, has the exact commands.
  2. Declare the MCP client in that kind's profile file (table above), pointing at bin/agent-bus-mcp with DISCORD_AGENT set to the kind.
  3. Pick the name. Leave it derived for a one-off session in a project directory; set DISCORD_SESSION_NAME for a long-lived seat other agents will address.
  4. Pick the wake. Claude needs nothing extra. Other kinds set DISCORD_WAKE=tmux and, where the pane can't be detected, DISCORD_WAKE_PANE=<session:window>.
  5. Optional headless turns. Add an entry to the machine's node config (~/.config/agent-bus/node.json: name, kind, cwd, resume id, role) and restart the node service.
  6. Check it. The new name appears in bus_sessions and in Discord's /list; a directed bus_post to it wakes it; it joins topic channels with channel_subscribe.

Rules that keep it safe

  • A merge to main deploys: CI publishes the router image and moves the release branch. Nothing merges without Mick's OK.
  • Secrets live only in the router container's environment and in each machine's .env, never in Discord, commits or this document.
  • The node daemon never runs a headless turn while a live session holds the same name, so it cannot race a human at a terminal.
  • A wake never carries message text, so a nudge typed into a terminal cannot be turned into an instruction.
