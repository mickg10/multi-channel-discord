## #22 · What protects the person at the keyboard

- **Codex 0.170/0.172.** Suppose the human submits a turn after the last status read and before the bus writes. The adapter sends only `thread/queue/add` for the bound thread. The daemon accepts the nudge while busy and dispatches it after the active turn. The producer never calls `turn/steer`, `turn/start` or `thread/queue/start`. The busy-turn and approval canaries verified that the owner kept control. Delete the unused public `probe()` wrapper. Keep the version check and the read-only `checkQueue` capability check inside `wake()`; an unsupported method or a recipient decision ends the attempt. Its queue read establishes support, never permission to interrupt. See #16 `adapters/codex.ts` lines 454–495 and design N2.
- **OpenCode 2.0.18.** The supported call is `POST /api/session/{id}/prompt` with `delivery:"queue"` and a stable message ID. The adapter checks the returned session ID, message ID, text and delivery mode. Its separate `probe()` reads the active map and checks only that it is an object; it never tests whether the target is idle. The recorded busy-session run rendered one queued turn after the active turn, and the permission test left the neighbouring session untouched and executed nothing after owner rejection. Neither adapter writes keystrokes into the composer. An unsent draft can still be overtaken by a queued turn on an idle runner; a busy probe cannot see or reserve that draft. If draft-first ordering is required for a scope, use pull-only there. Keep an attached-TUI check that a partially typed draft survives a nudge. No established atomic queue means no injection into a human-owned TUI. See #16 `adapters/opencode.ts` lines 99–103 and 121–149, and `deliver.ts` lines 39–46.

## #12(a) · What counts as an answer

- **One original message ID is minimal.** Two unanswered “Status?” posts in the same topic can receive different answers. Neither the channel nor the latest message identifies which one is resolved. Require `answers: X` when an elected master closes X via a human-directed post; leave it optional for ordinary chatter. Reuse the term fence and one-owner-or-answer record from #1. Validate the incumbent, original human message and term at commit. A normal `reply_to` only threads a Discord message and can even buffer a reply for an inactive chat (#20 `ws.ts` lines 968–997). It proves no disposition.
- **Persist the decision and the pending publication together.** Discord cannot take part in a local journal transaction. Today a human-only post can reach Discord before its publication is recorded (#20 `ws.ts` lines 1569–1585), and the legacy plugin reports success after a socket send (`plugin.ts` lines 755–772). For a closing answer, use a request-correlated call. Journal X, the answer payload and a stable publication ID before network I/O. On promotion, retry its pending mirror and any missing topic copy from that record; never ask the successor to compose the answer again. An ambiguous Discord acknowledgement can still leave external visibility uncertain. Test crashes on both sides of the send and an outage over five minutes. Bound each re-offer **batch**, retaining older unresolved work for later batches. A five-minute expiry can silently lose Mick’s unanswered post. The `reoffered` label and a history scan are unnecessary for deciding ownership once that durable record exists.
